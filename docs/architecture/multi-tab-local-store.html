タブ間でローカルストアは
共有されるのか

共有していなかった。いまは1つのコンテキストだけが開き、他はそこへ転送する。
以前は「タブ間で共有されない」のに「IndexedDB は物理的に共有されている」が同時に成り立っていた。それが問題の正体で、下の図1〜図2 がその状態。createSharedLocalStore がその差を埋めた。

問題 ── ストレージは4層あり、共有されるのは下2層だけ

読み取りはメモリ上の projection から返る。PGlite は読み取りパスではなく、オフライン書き込みを永続化するための durable store。その永続化の実体が2つとも IndexedDB なので、同一 origin のタブからは同じものが見えている。

層実体 / キータブ間
in-memory projection JS ヒープ 独立
liveClients ガード module scope の Set（client.ts:236） タブ内でしか効かない
PGlite の data dir idb://photon-engine-<scope> 物理的に共有
commit journal photon-commit-journal:<dataDir> 物理的に共有

壊れ方は2つある

FAILURE 1

PGlite は data dir あたり単一接続前提

2タブ目が同じ dir を開くと、それぞれが自分の WASM メモリ上に独立した Postgres 状態を持ったまま、同じ IndexedDB ファイル群に書き戻す。互いのページを踏み潰す。

FAILURE 2

journal の seq が衝突する

journalSeq はインスタンスごとの in-memory カウンタで、boot 時に checkpoint 行から初期化されるだけ。2タブが同時に開けば両方が同じ番号を採番する。

それまでの逃げ道は exclusiveLock ひとつだった

Web Locks で photon-pglite:<dataDir> を掴む opt-in オプション。ifAvailable: true なので待たずに即失敗する ── ロック待ちでハングするのは「壊れた」と見分けがつかないため。いまも残っているが、これは「2タブ目を調停するくらいなら断る」ホスト向けの選択肢になった。

OFF ／ デフォルト

静かに壊れる

2タブ目もそのまま開く。図1・図2 の状態に入り、エラーは出ない。壊れたことに気づくのはリロード後。

ON ／ opt-in

はっきり落ちる

2タブ目は PGliteStoreLockedError で開けない。takeover のストーリー（leader election / SharedWorker）がない以上、選べるのはこの2択しかない、という設計判断。

では、タブ間の整合はどう取れているのか

サーバ経由。「一方のタブでの編集が他方に見える」という動作は成立しているが、それはローカルストアを共有しているからではなく、push → サーバ → pull で一周しているから。

Tauri でも、いまはまったく同じ話

Tauri のフロントエンドは WebView なので、複数ウィンドウは同一 origin の別コンテキストになり、同じ IndexedDB を見る。Tauri 固有の緩和は入っていない（packages/ の store adapter は store-pglite のみ）。

ただし本来は Tauri のほうが解きやすい

Rust 側に単一 writer を置ける

Rust に SQLite を置いて LocalStore を実装すれば、全ウィンドウが1プロセスの writer を IPC 越しに共有でき、ロックも直列化も OS 側で成立する。LocalStore が意図的に約10メソッドに絞られているのはこの差し替えのためだが、その adapter はまだ書かれていない。

実装した形

createSharedLocalStore。1つのコンテキストだけが実体を開き、残りは転送する。オーナーのタブが閉じたら、Web Locks の待ち行列で次が昇格して自分で開き直す。

なぜ小さく済むのか

LocalStore が約10個の冪等メソッドしかない

だから「別コンテキストへ転送する」実装が小さなオブジェクトで済み、失った応答を再送しても安全になる。継ぎ目を最初から狭く切っておいた効果がここで出た。

transport は差し替え可能

BroadcastChannel ＋ Web Locks

Android の WebView を含む全ターゲットで動く唯一の組み合わせ。SharedWorker や Tauri の Rust 側に載せ替えるときは channel と elect を差し替えるだけで、この上のコードは変わらない。

残っている無駄

同期ループは全タブで走ったまま

N タブなら N 回 pull する。壊れはしない ── 永続 cursor を単調にしたので巻き戻らず、書き込みは全て冪等。オーナーだけが同期する形にするのは別の変更。

残っている限界

配るのはレコードで、オペレーションではない

受け側はカーネルで再マージしない。2タブが同一レコードの別フィールドを同時に編集すると、ローカルでは後勝ちで片方が消える。オペレーションは両方保存・push されるのでサーバが正しくマージして pull で直るが、オフライン中は直らない。オペレーションを配る形にするには、2タブが同一 actorId を共有するのをやめる必要がある ── でないと HLC が衝突しうる。
