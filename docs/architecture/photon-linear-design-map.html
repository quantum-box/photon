Photon × Linear 設計マップ

Linearの速さの技術分解(performance.dev)をPhotonの現在地に重ねた整理。結論: Engine/Liveの分離と楽観書き込みはLinearの実構成と同型で実装済み。残るギャップは読み取り粒度(field単位)・lazy hydration・pull通知の3点。

01Linearの設計思想と3本柱

速さは単一の技術ではなく設計思想の積み重ね。UIの応答性をネットワークレイテンシから切り離すことがすべての出発点。

Database in the BrowserUIが読むDBはブラウザ内にある

IndexedDBからメモリ上のobject poolへhydrateし、UIのクエリはすべてpoolに向く。サーバーはsync target。

Photon: projection pool + PGliteで実装済み ✓

Mutations Don't Wait書き込みはネットワークを待たない

observable更新(即UI反映)・ローカルDB書き込み・serverキュー投入を同時に実行。rejectされた時だけrevert。

Photon: 楽観apply + pending op + rollbackで実装済み ✓

One Delta, One Cell1フィールドの更新は1セルだけ再描画

プロパティ単位のobservableで、50件の更新は「50セルの再描画」で済む。リスト全体は動かない。

Photon: record粒度まで実装済み、field粒度が残り

"UI responsiveness should not depend on network latency"
サーバーはsource of truthではなくsync target。この前提がスピナーの排除・楽観UI・オフライン対応をすべて同じ仕組みで説明する。

03core読み取り層の現在地

UIはPGliteに直接クエリせず、メモリ上のprojection poolを読む — この構造は実装済み。PGliteはhydration元 + 耐久化先。Liveはcoreの正しさに関与しないpluginとして横に置く。残りはUI最上段の購読粒度。

UI 1 delta = 1 cell re-render / ここが残り

useLiveQuery / useRecord は実装済み。field単位の useRecordField 系selectorを足し、全records配列のContext配布をセル購読に置き換える。

subscribe / mutate

in-memory projection pool core / 実装済み

LinearのMobX pool相当。書き込みは operation生成 → projection即時更新 → PGlite書き込み → push queue と一気に流れ、record objectは変更時のみ再割り当て。

hydrate / persist

PGlite projections + pending op log

構造は即時hydrate、recordはビュー表示時にオンデマンド。cursorもここに永続化。

push / pull

Engine server edge → cloud authority

business logic検証 → accepted op + remote_sequence。ここは実装済みの領域。

Photon Live(plugin)

presence / awareness / リッチテキスト共同編集(将来のview editor・docs)。Yjsはここに閉じる。

→ core接点は「pullすべき変更がある」という通知のみ

畳む対象

RecordsContextの「全records配列をContextで配布」するパス。field購読への移行後、Contextは書き込みハンドラだけに痩せる。

04優先順位

上から順に効果が大きい。いずれもEngine client APIの上のレイヤーなので、PLT-3072〜3074と独立に着手できる。

field粒度の購読(useRecordField)

coreにfield selector付きLiveQueryを追加し、photon-reactに useRecordField を生やす。テーブルセル・Boardカードをfield購読に移行し、「1 delta = 1 cell」を完成させる。

lazy hydration(起動コスト ∝ 構造)

bootstrapでdatabases / viewsの構造だけhydrateし、recordはビュー表示時にPGliteから引く。1万record時代でも100 record時と同じ起動速度を目標値にする。

Liveをpullヒントに

sync loopの既存トリガー(boot / online / visibility / reconnect)に加え、Liveチャネル経由の「変更あり」通知でpullを起こす。ポーリングなしでdelta到達が速くなり、Live障害はcoreに波及しない。

独立して進められる小粒トラック

  • Render-first auth — localStorageのtoken + PGliteがあればhappy pathを仮定して即shell表示、検証は裏で。401時のみredirect
  • Viteビルド最適化 — target: esnext / lightningcss / package単位manualChunks / modulepreload。Web版はService Worker precacheでオフライン起動
  • ⌘K コマンドパレット — ローカルpool / PGliteだけで検索。「サーバーを待たない検索」はlocal-firstのショーケース
  • アニメーションtoken — transform / opacity + paint-only propertyに限定。duration 0.1〜0.35s、enterは即時・exitのみfade
